Lesson 01 GitHub Actions 零基礎友善

GitHub Actions 完全入門：看懂我們的 deploy.yml 與 update-data.yml

1. 什麼是 GitHub Actions？

平常你在自己電腦上開發時，如果你想更新網站，必須手動做這些事：打開電腦 → 跑 python scraper/main.py → 跑 npm run build → 把打包好的網頁上傳到主機。

GitHub Actions 就是 GitHub 免費借你一台「雲端臨時電腦（Ubuntu Linux）」，你只要把操作步驟寫成一份清單放在 .github/workflows/ 資料夾裡，只要時間到了或你推程式碼上去，GitHub 就會自動開機、照你的清單把事情做完、做完再自動關機。

💡 生活比喻：把 GitHub Actions 想成「自動化工廠的 SOP 說明書」
  • .github/workflows/*.yml：就是你寫給機器人的 SOP 說明書（使用 YAML 格式，靠縮排表達階層）。
  • Runner（ubuntu-latest）：每次要執行時，GitHub 現場幫你租一台全新的 Linux 電腦（用完即丟，乾乾淨淨）。
  • GitHub Pages：免費的靜態網站空間，把打包好的 HTML/CSS/JS 放進去，全世界就能用網址打開看。

2. 必學的 6 個關鍵名詞

看懂這 6 個詞，你就能看懂網路上 90% 的 GitHub Actions 設定檔：

1. Workflow（工作流程） 就是 .github/workflows/ 裡的一份 .yml 檔案。我們有兩個：一個負責抓價，一個負責部署。
2. Trigger（觸發條件：on:） 決定「什麼時候啟動」這份流程。例如：push（推程式碼時）、schedule（定時）、workflow_dispatch（手動按按鈕）。
3. Job（工作站：jobs:） 一個 Workflow 裡面可以分好幾個 Job（例如 build 和 deploy）。每個 Job 都在一台獨立的全新電腦上跑。
4. Runner（執行電腦：runs-on:） 這台雲端電腦要裝什麼作業系統。我們用 ubuntu-latest（最新免費 Linux），啟動快又穩定。
5. Step（步驟：steps:） 在同一個 Job 裡，照順序一條條執行的指令。可以用 run: 跑終端機指令，或用 uses: 套用別人寫好的積木。
6. Action（現成積木：uses:） 像 actions/checkout@v7 就是 GitHub 官方寫好的現成工具，幫你把程式碼下載到雲端電腦，不用自己寫一堆指令。

3. 為什麼我們要拆成兩個檔案？

你可能會想：「全部寫在同一份 YAML 不行嗎？」其實可以，但拆成兩份有一個超大的好處——分工清楚、不浪費時間：

情境 會觸發哪一個 Workflow？ 實際會做什麼？
你改了 Vue 畫面（例如改按鈕顏色）並 git push 只跑 deploy.yml 直接打包 Vue → 部署網頁（約 30 秒），不用重跑爬蟲！
每天台灣時間 09:00 / 21:00（或手動點 Run） 跑 update-data.yml 先跑 Python 爬蟲 → 如果價格有變動，存檔回 GitHub → 再呼叫 deploy.yml 更新網站！

兩份檔案的串聯流程圖

1
時間到（09:00 / 21:00）或手動觸發 update-data.yml
開啟一台 Ubuntu 電腦執行 scrape Job
↓
2
執行 python scraper/main.py
讀取 data/catalog.json + 查台灣價格 API → 更新 history.json 與 games.json
↓
3
檢查檔案有沒有變動（git diff）
有變動才 git commit & push 回 main 分支，並輸出 changed=true
↓
4
呼叫可重用的 deploy.yml（uses: ./.github/workflows/deploy.yml）
打包 Vue 專案（npm run build）→ 上傳產物（Artifact）→ 部署上 GitHub Pages！

4. 逐行拆解 #1：.github/workflows/deploy.yml

這份檔案只專心做一件事：把 frontend/ 裡的 Vue 原始碼編譯成靜態網頁，放到 GitHub Pages 上。

前半段：什麼時候啟動？需要什麼權限？

name: Deploy Frontend to GitHub Pages

on:
  push:
    branches: [main]
    paths:                          # 只有改到前端或 deploy.yml 本身才觸發
      - 'frontend/**'
      - '.github/workflows/deploy.yml'
  workflow_dispatch:                # 允許你在 GitHub 網頁手動按「Run workflow」
  workflow_call:                    # 關鍵！允許「別的 workflow」（update-data.yml）來呼叫它

permissions:                        # 最小權限原則：只給部署 Pages 必要的權限
  contents: read                    # 讀取程式碼
  pages: write                      # 寫入 GitHub Pages
  id-token: write                   # GitHub Pages 部署身分驗證

concurrency:                        # 排隊機制：同時間只允許一個部署在跑，避免互蓋
  group: pages
  cancel-in-progress: false         # 不要砍掉正在部署到一半的工作，讓它跑完

後半段：兩個 Job（先 Build，再 Deploy）

jobs:
  build:                            # 工作站 1：負責把 Vue 打包成 dist/
    runs-on: ubuntu-latest
    steps:
      - name: Checkout              # Step 1：把 repo 程式碼抓進這台雲端電腦
        uses: actions/checkout@v7
        with:
          ref: main                 # 強制抓 main 最新版（原因見第 7 節！）

      - name: Setup Node.js         # Step 2：安裝 Node.js 22 並快取 npm 套件加速
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          cache: 'npm'
          cache-dependency-path: frontend/package-lock.json

      - name: Install dependencies  # Step 3：進 frontend/ 裝套件
        working-directory: frontend
        run: npm install

      - name: Build Vue app         # Step 4：型別檢查 + Vite 打包出 frontend/dist/
        working-directory: frontend
        run: npm run build

      - name: Setup Pages           # Step 5：初始化 GitHub Pages 環境
        uses: actions/configure-pages@v5

      - name: Upload artifact       # Step 6：把 frontend/dist 打包成「貨物（Artifact）」交給下一站
        uses: actions/upload-pages-artifact@v3
        with:
          path: frontend/dist

  deploy:                           # 工作站 2：把剛剛的貨物發佈上線
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build                    # 一定要等 build 成功後才開始跑 deploy！
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
📦 什麼是 Artifact（產物）？
因為 build 和 deploy 是兩台不同的臨時電腦，build 做完的 frontend/dist/ 檔案在關機後會消失。所以要用 upload-pages-artifact 先把成品打包寄存在 GitHub 倉庫裡，下一站 deploy 再去領取並發佈到網站。

5. 逐行拆解 #2：.github/workflows/update-data.yml

這份檔案負責定時跑 Python 爬蟲、把最新價格存回 GitHub，然後叫 deploy.yml 上線。

name: Update Taiwan eShop Prices

on:
  schedule:
    - cron: '0 1,13 * * *'          # UTC 01:00 與 13:00 = 台灣時間 09:00 與 21:00
  workflow_dispatch:                # 手動執行時，還讓你填一個小表單（輸入頁數限制）
    inputs:
      max_hk_pages:
        description: '限制香港商店頁數（0 代表抓取全部）'
        required: false
        default: '0'

permissions:
  contents: write                   # 注意！這裡要 write，因為機器人要 git push 新資料回 repo
  pages: write
  id-token: write

jobs:
  scrape:                           # 工作站 1：抓資料
    runs-on: ubuntu-latest
    outputs:                        # 把「資料有沒有變動」的結果傳給下一個 Job
      changed: ${{ steps.commit.outputs.changed }}
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup Python          # 裝 Python 3.12（我們沒用外部套件，連 pip install 都省了！）
        uses: actions/setup-python@v7
        with:
          python-version: '3.12'

      - name: Run Taiwan eShop scraper
        run: python scraper/main.py --max-hk-pages "${{ github.event.inputs.max_hk_pages || '0' }}"

      - name: Commit updated data and price history
        id: commit                  # 給這步驟取個名字，上面的 outputs 才能抓到它
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add data/catalog.json data/history.json frontend/public/data/games.json
          if git diff --cached --quiet; then
            echo "changed=false" >> "$GITHUB_OUTPUT"
            echo "No data changes detected."
          else
            git commit -m "chore(data): update TW eShop prices [skip ci]"
            git push
            echo "changed=true" >> "$GITHUB_OUTPUT"
          fi

  deploy:                           # 工作站 2：條件符合才呼叫 deploy.yml
    needs: scrape
    if: needs.scrape.outputs.changed == 'true' || github.event_name == 'workflow_dispatch'
    uses: ./.github/workflows/deploy.yml
    permissions:
      contents: read
      pages: write
      id-token: write
這段 if git diff --cached --quiet 在幹嘛？

它是在問 Git：「剛才 git add 的三個資料檔，跟原本比起來有沒有任何變化？」
• 如果完全沒變（--quiet 回傳成功）：就不 commit、不 push，設定 changed=false，跳過無謂的部署。
• 如果有價格變動或新特價：就以機器人身分 commit 並 push 回 main，設定 changed=true，接著自動觸發 deploy Job！

6. 看懂 Cron 定時語法

GitHub Actions 的定時排程（schedule）用的是 Linux 經典的 5 欄位 Cron 語法，而且一律使用 UTC（世界協調時間），不是台灣時間（UTC+8）！

0
分鐘 (0-59)
1,13
小時 (0-23, UTC)
*
每月幾號 (每日)
*
月份 (每月)
*
星期幾 (每天)

所以 '0 1,13 * * *' 的意思就是：
每天 UTC 01:00（+8 = 台灣早上 09:00）和 UTC 13:00（+8 = 台灣晚上 21:00）的整點 0 分各跑一次！

常見範例 代表意思（換算成台灣時間 UTC+8）
0 1 * * *每天台灣時間早上 09:00 跑一次
30 14 * * *每天台灣時間晚上 22:30 跑一次
0 */6 * * *每 6 小時跑一次（00:00 / 06:00 / 12:00 / 18:00 UTC）
0 1 * * 1每週一台灣時間早上 09:00 跑一次

7. 實戰才學得到的 3 個真實小坑（我們剛才真的踩過！）

看教學文章很少人講，但自己動手做一定會遇到——這三個都是我們今天剛解掉的真實案例：

坑 #1：為什麼 deploy.yml 一定要加 ref: main？

當 update-data.yml 啟動時，GitHub 會把「當下的 commit（假設叫版本 A）」記成 github.sha。就算第一個 Job scrape 推了新資料（版本 B），如果第二個 Job 呼叫 deploy.yml 時沒寫 ref: main，actions/checkout 預設還是會抓「觸發當下的版本 A」，導致你明明抓完新價格，網頁卻還是舊的！加上 ref: main 就會明確抓 main 分支最新的版本 B。

坑 #2：為什麼 commit 訊息後面寫了 [skip ci]？

這是一個好習慣：告訴 GitHub「這個機器人自動產生的資料 commit，不要再去額外觸發其他 CI 流程」，避免重複跑兩次部署，或不小心造成「機器人推資料 → 觸發流程 → 機器人又推資料」的無限迴圈。（雖然 GitHub 預設用 GITHUB_TOKEN 推的 commit 本來就會擋掉連鎖觸發，但加上 [skip ci] 讓意圖更清楚。）

坑 #3：為什麼會有「Node.js 20 is deprecated」警告？

像 actions/checkout@v4 這種官方積木，背後其實是用 Node.js 寫的小程式。當 GitHub 在 2026 年淘汰 Node 20 執行環境、改用 Node 24 時，舊版積木（@v4 / @v5）就會跳出黃色棄用警告。解法很簡單：把積木版本升級到支援 Node 24 的最新版本（@v7）就乾淨了！
